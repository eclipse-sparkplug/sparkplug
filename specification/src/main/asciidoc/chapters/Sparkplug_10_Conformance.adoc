[[conformance]]
== Conformance

[[conformance_profiles]]
=== Conformance Profiles

There are four Sparkplug target applications. A Sparkplug infrastructure typically consists of one
or more of the following application types

* Sparkplug Edge Node
* Sparkplug Host Application
* Sparkplug Compliant MQTT Server
* Sparkplug Aware MQTT Server

Each application type has specific conformance requirements that must be met. Typically a Sparkplug
application would only implement one of these profiles. For example an MQTT client wouldn't
typically be both an Edge Node and a Host Application.

[[conformance_sparkplug_edge_node]]
==== Sparkplug Edge Node

A Sparkplug Edge Node is typically an 'Edge Gateway'. It sends and receives data to an MQTT Server
using a Sparkplug namespace, either spCv4.0/# or spJv4.0/#. Edge Nodes typically interact with
physical devices to gather data and also write to device outputs.

Sparkplug defines two payload encodings, as described in the
link:#payloads_json_encoding_selection[Encoding Selection] section. An Edge Node is not required to
implement both.

* [tck-testable tck-id-conformance-edge-node-encoding-one]#[yellow-background]*[tck-id-conformance-edge-node-encoding-one] A
Sparkplug Edge Node MUST support at least one of the two Sparkplug payload encodings, and MUST
publish on the namespace that corresponds to the encoding it uses.*#
* [tck-not-testable tck-id-conformance-edge-node-encoding-both]#[yellow-background]*[tck-id-conformance-edge-node-encoding-both] A
Sparkplug Edge Node MAY support both payload encodings, in which case the encoding it uses is
selected by configuration.*#
* [tck-testable tck-id-conformance-edge-node-encoding-session]#[yellow-background]*[tck-id-conformance-edge-node-encoding-session] A
Sparkplug Edge Node MUST publish every message of an MQTT session using a single payload encoding on
the corresponding single namespace.*#
* [tck-testable tck-id-conformance-edge-node-encoding-subscribe]#[yellow-background]*[tck-id-conformance-edge-node-encoding-subscribe] A
Sparkplug Edge Node MUST subscribe to its command topics on the same namespace it publishes on, so
that a Host Application addressing it on that namespace reaches it.*#
** Non-normative comment: an Edge Node has one sequence number stream, so publishing part of a
session on one namespace and part on the other would leave a consumer of either namespace with gaps
in that stream.

Support for strongly typed commands is optional. An Edge Node that exposes commands must do so in a
conformant manner.

* [tck-testable tck-id-conformance-edge-node-command-response]#[yellow-background]*[tck-id-conformance-edge-node-command-response] A
Sparkplug Edge Node that includes Command metrics in its NMETA or DMETA MUST respond to command
requests with NRESP or DRESP command responses as defined in the
link:#operational_behavior_commands_typed[Typed Commands and Command Responses Section].*#
* [tck-testable tck-id-conformance-edge-node-nmeta]#[yellow-background]*[tck-id-conformance-edge-node-nmeta] A
Sparkplug Edge Node MUST publish an NMETA describing its own metric structure and a DMETA describing
each of its Devices' metric structures, following all NMETA/DMETA topic and payload requirements.*#
* [tck-testable tck-id-conformance-edge-node-birth-value-only]#[yellow-background]*[tck-id-conformance-edge-node-birth-value-only] A
Sparkplug Edge Node MUST publish NBIRTH and DBIRTH messages as value-only messages that reference the
corresponding NMETA/DMETA by definition identifier and identify each metric by its alias or name.*#
* [tck-testable tck-id-conformance-edge-node-mmeta]#[yellow-background]*[tck-id-conformance-edge-node-mmeta] A
Sparkplug Edge Node that changes its metric structure after BIRTH MUST express the change as an
NMMETA/DMMETA with per-metric operations (ADD, UPDATE, DELETE), and MUST also publish an updated full
NMETA/DMETA with retain true, rather than requiring a full Rebirth.*#

[[conformance_sparkplug_host_application]]
==== Sparkplug Host Application

A Sparkplug Host Application is typically at a 'central location' and primarily receives data from
multiple Sparkplug Edge Nodes. It also may send command messages to Sparkplug Edge Nodes to write to
outputs of Sparkplug Edge Nodes and/or Devices. Sparkplug Host Applications may also sends rebirth
requests to Edge Nodes when required.

A Sparkplug Host Application is not required to consume an entire Sparkplug namespace. A Host
Application that is interested in a single Sparkplug Device, or in a handful of them, may narrow its
subscriptions accordingly. Such a Host Application is conformant only if it also meets the
requirements in the
link:#operational_behavior_host_application_partial_subscriptions[Host Applications with Partial
Subscriptions] section, which cover the subscriptions it must still hold (in particular the NBIRTH,
NREBIRTH, and NDEATH of every Edge Node reporting a Device of interest, which carry the Edge Node
state that encapsulates the state of its Devices) and its use of the descriptor sequence number in
place of the Edge-Node-wide sequence number.

A Sparkplug Host Application consumes data produced by Edge Nodes that it does not control, and so
cannot assume which payload encoding those Edge Nodes use.

* [tck-testable tck-id-conformance-host-encoding-both]#[yellow-background]*[tck-id-conformance-host-encoding-both] A
Sparkplug Host Application MUST support both Sparkplug payload encodings, and MUST be able to
consume messages on both the spCv4.0 and spJv4.0 namespaces.*#
* [tck-testable tck-id-conformance-host-encoding-publish]#[yellow-background]*[tck-id-conformance-host-encoding-publish] When
a Sparkplug Host Application publishes a message, it MUST encode that message using the encoding
that corresponds to the namespace it publishes on.*#
* [tck-testable tck-id-conformance-host-encoding-address]#[yellow-background]*[tck-id-conformance-host-encoding-address] When
a Sparkplug Host Application publishes a message addressed to a particular Edge Node or Device,
including an NCMD, a DCMD, and a Rebirth Request, it MUST publish on the namespace of that Edge
Node's current NBIRTH.*#
** Non-normative comment: a Host Application supports both encodings, so without this it could
address an Edge Node on a namespace that Edge Node does not subscribe to. The message would be
accepted by the MQTT Server and never delivered, and a Rebirth Request in particular would fail
silently, leaving the Host unable to recover its view of that Edge Node.
** Non-normative comment: which namespaces a Host Application subscribes to remains a deployment
decision. The requirement is that it is capable of decoding either, so that an Edge Node's choice of
encoding does not determine which Host Applications can consume it. This is the property that makes
the two encodings interoperable rather than two separate ecosystems.

[tck-testable tck-id-conformance-primary-host]#[yellow-background]*[tck-id-conformance-primary-host] Sparkplug
Host Applications MUST publish 'STATE' messages that represent its Birth and Death Certificates.*#

Support for invoking strongly typed commands is optional. A Host Application that invokes commands
must do so in a conformant manner.

* [tck-testable tck-id-conformance-host-command-request]#[yellow-background]*[tck-id-conformance-host-command-request] A
Sparkplug Host Application that invokes a Command MUST send the command request and process the
NRESP or DRESP command response as defined in the
link:#operational_behavior_commands_typed[Typed Commands and Command Responses Section].*#
* [tck-testable tck-id-conformance-host-nmeta-resolve]#[yellow-background]*[tck-id-conformance-host-nmeta-resolve] A
Sparkplug Host Application MUST resolve metrics in an NBIRTH/DBIRTH/NDATA/DDATA (whether identified
by alias or by name) against the metric definitions in the NMETA/DMETA sharing the same definition
identifier.*#
* [tck-testable tck-id-conformance-host-nmeta-missing]#[yellow-background]*[tck-id-conformance-host-nmeta-missing] If
a Host Application receives a value message whose definition identifier does not match a known
NMETA/DMETA, it MUST obtain the matching metadata (from the retained NMETA/DMETA message on its
Sparkplug topic) before treating the metric structure as complete, and MAY issue a REBIRTH request.*#
* [tck-testable tck-id-conformance-host-mmeta]#[yellow-background]*[tck-id-conformance-host-mmeta] A
Sparkplug Host Application MUST apply an NMMETA/DMMETA whose previous definition identifier matches
its current definition identifier for the Edge Node/Device, MUST recompute the definition identifier,
and on mismatch MUST obtain the full metadata or issue a REBIRTH request. If the previous definition
identifier does not match, it MUST NOT apply the operations.*#

[[conformance_mqtt_server]]
==== Sparkplug Compliant MQTT Server

Sparkplug infrastructures have a specific subset of requirements on MQTT Servers. Any fully MQTT
v3.1.1 or v5.0 MQTT Server will meet the requirements of Sparkplug infrastructures. However, not all
of the features of the MQTT Specification are required. The following are the required portions of
the MQTT Specification that a Sparkplug Compliant MQTT Server must meet.

* [tck-testable tck-id-conformance-mqtt-qos0]#[yellow-background]*[tck-id-conformance-mqtt-qos0] A
Sparkplug conformant MQTT Server MUST support publish and subscribe on QoS 0*#
* [tck-testable tck-id-conformance-mqtt-qos1]#[yellow-background]*[tck-id-conformance-mqtt-qos1] A
Sparkplug conformant MQTT Server MUST support publish and subscribe on QoS 1*#
* [tck-testable tck-id-conformance-mqtt-will-messages]#[yellow-background]*[tck-id-conformance-mqtt-will-messages] A
Sparkplug conformant MQTT Server MUST support all aspects of Will Messages including use of the
'retain flag' and QoS 1*#
* [tck-testable tck-id-conformance-mqtt-retained]#[yellow-background]*[tck-id-conformance-mqtt-retained] A
Sparkplug conformant MQTT Server MUST support all aspects of the 'retain flag'*#

Non-normative comment: a Sparkplug Compliant MQTT Server has no payload requirements of any kind. It
treats a Sparkplug payload as an opaque sequence of bytes, so both payload encodings are carried by
the same server with no additional support.

[[conformance_sparkplug_aware_mqtt_server]]
==== Sparkplug Aware MQTT Server

A 'Sparkplug Aware' MQTT Server includes all of the aspects of a Sparkplug Compliant MQTT Server.

In Sparkplug, an Edge Node's and each Device's metric structure (metadata) is carried in NMETA and
DMETA messages that are published with the MQTT retain flag set to true. The current metadata is
therefore retained and delivered to subscribing clients by any Sparkplug Compliant MQTT Server
through the normal MQTT retain mechanism, including while the Edge Node is offline. As a result, a
Sparkplug Aware MQTT Server is NOT required to store NBIRTH or DBIRTH messages, and is NOT required to
republish metadata on a $sparkplug topic. Metric structure discovery is provided directly by the
retained NMETA and DMETA messages on their normal Sparkplug topics. NBIRTH and DBIRTH messages
continue to be published with the MQTT retain flag set to false and are not retained.

* [tck-testable tck-id-conformance-mqtt-aware-basic]#[yellow-background]*[tck-id-conformance-mqtt-aware-basic] A
Sparkplug Aware MQTT Server MUST support all aspects of a Sparkplug Compliant MQTT Server*#
* [tck-testable tck-id-conformance-mqtt-aware-encoding-both]#[yellow-background]*[tck-id-conformance-mqtt-aware-encoding-both] A
Sparkplug Aware MQTT Server that replaces NDEATH timestamps MUST do so for payloads in both
encodings, on both the spCv4.0 and spJv4.0 namespaces.*#
** Non-normative comment: replacing an NDEATH timestamp is the only behavior required of a
Sparkplug Aware MQTT Server that decodes a payload at all, and it is itself optional. A Server that
does not do it never inspects a payload and needs neither encoding. The requirement is therefore
conditional, so that offering the timestamp behavior for one encoding only cannot leave Edge Nodes
on the other namespace silently unserved.
* [tck-testable tck-id-conformance-mqtt-aware-ndeath-timestamp]#[yellow-background]*[tck-id-conformance-mqtt-aware-ndeath-timestamp] A
Sparkplug Aware MQTT Server MAY replace the timestmap of NDEATH messages. If it does, it MUST set
the timestamp to the UTC time at which it attempts to deliver the NDEATH to subscribed clients*#
